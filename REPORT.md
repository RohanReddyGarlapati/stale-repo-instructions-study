# Do Stale Repository Instructions Mislead AI Coding Agents?

**A preregistered study of stale file-path guidance and Claude Code**

Rohan Reddy Garlapati · October 2026 · Protocol frozen at git tag `prereg-v1` (commit `57dc567`)

## Summary

Repository instruction files such as `CLAUDE.md` can fall out of date as code is renamed. This study measures what happens when one fact in such a file, the path of the file a bug fix belongs in, is stale. On 23 real issue-resolution tasks from three open-source JavaScript and TypeScript repositories, Claude Code was run under three conditions (accurate guidance, stale guidance, no guidance), four times each, for 276 valid runs.

- **Effort:** stale guidance was associated with about 0.76 more tool calls per run than accurate guidance (9.30 vs 8.54, roughly 9% more). The bootstrap 95% interval is [+0.07, +1.49]; the sign-flip test gives p = 0.056. This is borderline evidence of a small effort cost.
- **Success:** on the 12 tasks of intermediate difficulty, success was 62.5% with stale guidance and 70.8% with accurate guidance. The difference (−8.3 points, 95% interval [−27.1, +8.3], p = 0.54) is not distinguishable from zero, and the comparison is underpowered.
- **Behaviour:** in 21 of 92 stale-condition runs (23%) the agent went to the stale path before the correct one.
- **Accurate guidance showed no detectable benefit** over no guidance.

## 1. Question

How much does task-relevant stale repository guidance change a coding agent's issue-resolution success and effort, compared with accurate guidance and no guidance?

Related work: Gloaguen et al. (2026) evaluated repository context files such as `AGENTS.md` and reported no improvement in task success and over 20% higher inference cost; the arXiv v1 abstract says success tended to be reduced. That work compares having a context file against not having one. This study asks a narrower question about the content of the file: what happens when one fact in it is out of date.

## 2. Method

### 2.1 Tasks

Tasks come from Multi-SWE-bench (Zan et al., 2025), which pairs real fixed issues with tests that fail before the fix and pass after it. The candidate pool was built mechanically from the TypeScript and JavaScript tasks of the full set (580 tasks, 9 repositories) by `scripts/select_pool.py`, under the rubric in `preregistration/task-selection.md`, written before any agent run:

- The reference fix changes 3 or fewer files.
- At least one non-test file in the fix was renamed or moved earlier in repository history, with the most recent such rename at most 730 days before the task's base commit.
- After a seeded shuffle (seed 20261007): at most 3 tasks per rename event and at most 20 per repository.

This produced a pool of 50 tasks. Each was validated by applying its reference fix and running the benchmark tests; six material-ui tasks failed this first validation and were excluded, leaving 44 valid tasks.

A pilot of five tasks (30 runs) showed that when a fix spans several source files, the agent may work in a file the instruction file never mentions. A relevance rule was therefore added before screening: the fix must change the renamed file as its only source file, and the reference fix must pass three independent validation runs. Both rules are recorded in Amendment 1.1 of `PROTOCOL.md` (2026-10-07, before screening), which also narrowed the study to the stale-file-path category. With both rules applied and the pilot tasks set aside, 23 tasks were eligible for screening (Amendment 1.2). Of the 50 pool tasks, 42 passed three of three validations; a single validation would have admitted 44.

The 23 tasks come from sveltejs/svelte (16), mui/material-ui (5) and vuejs/core (2). The protocol allowed up to 25 study tasks from at least five repositories. The five-repository minimum could not be met with tasks that passed the validity rules, because the only eligible task from a fourth repository had unreliable tests (Amendment 1.2, 2026-10-07, before screening).

### 2.2 Conditions

Each task has an accurate and a stale `CLAUDE.md`, generated by `scripts/make_guides.py` from one template: the target file plus up to two alphabetically first source files from the same folder, and a fixed conventions section. The two versions differ in exactly one line. The accurate version gives the target file's path at the base commit; the stale version gives its path before the rename, which does not exist at the base commit. The third condition has no instruction file. `manifests/conditions.tsv` records the line differences and file hashes per task.

### 2.3 Agent and procedure

- **Agent:** Claude Code 2.1.292 with model `claude-sonnet-5-5`, run non-interactively inside the task's Docker container with Bash, Read, Edit, Write, Glob and Grep only. Web tools and MCP connectors were disabled. Auto-update was disabled.
- **Preparation:** the reference fix and test patches were deleted from the container and the repository history was replaced by a single fresh commit, so the earlier path could not be found in history.
- **Schedule:** 23 tasks × 3 conditions × 4 repeats = 276 runs, with conditions shuffled within each task and repeat (seed 20261013).
- **Scoring:** the agent's changes were scored with the Multi-SWE-bench harness.

### 2.4 Measures and analysis

- **Effort (primary, H2):** tool calls per run, on all 23 tasks.
- **Success (primary, H1):** benchmark tests pass or fail, on the 12 tasks that the screening stage (three no-guidance runs of each of the 23 tasks, 69 runs) solved in one or two of three runs. Tasks solved always or never offer little room to show a difference.
- **Stale-following:** whether the agent used the stale path before the correct one, coded automatically from the trace (`scripts/code_traces.py`).

The primary contrast is stale minus accurate. Intervals are bootstrap intervals (10,000 resamples, seed 20261012) and p-values come from a sign-flip test, both computed by `analysis/primary_analysis.py`, whose code is unchanged from the `prereg-v1` tag. The unit of analysis is the task: the repeats of each task and condition are averaged, one difference is computed per task, and the bootstrap resamples those per-task differences with replacement (percentile intervals). The sign-flip test randomly flips the sign of each task's difference.

## 3. Results

276 valid runs. Estimated cost $32.02 in total (about $0.12 per run, `results/confirmatory/cost.txt`); mean run time 44 seconds. No run was flagged for network use.

### 3.1 Primary contrasts

| Outcome | Set | None | Accurate | Stale | Stale minus accurate | 95% interval | Sign-flip p |
|---|---|---|---|---|---|---|---|
| Tool calls per run (H2) | 23 tasks | 8.70 | 8.54 | 9.30 | +0.76 | [+0.07, +1.49] | 0.056 |
| Task success (H1) | 12 tasks | 72.9% | 70.8% | 62.5% | −8.3 points | [−27.1, +8.3] | 0.54 |

### 3.2 Other contrasts (tool calls, 23 tasks)

| Contrast | Difference | 95% interval | Sign-flip p |
|---|---|---|---|
| Stale minus none | +0.61 | [−0.16, +1.40] | 0.16 |
| Accurate minus none | −0.15 | [−0.71, +0.40] | 0.63 |

### 3.3 By repository (tool calls, stale minus accurate)

| Repository | Tasks | Difference |
|---|---|---|
| sveltejs/svelte | 16 | +0.7 |
| mui/material-ui | 5 | +0.2 |
| vuejs/core | 2 | +2.9 |

The direction is the same in all three. None is conclusive on its own, and the vuejs/core figure rests on two tasks.

### 3.4 Stale-following

The agent used the stale path first in 21 of 92 stale-condition runs (23%). Most of these runs recovered and the task was still solved. The count comes from `results/confirmatory/trace_coding.tsv`; the frozen analysis output reports 93 because it included a superseded run (see `DEVIATIONS.md`, item 7).

## 4. Interpretation

Stale path guidance appears to cost a small amount of extra work. The evidence is borderline: the interval excludes zero narrowly and the sign-flip test does not reach p < 0.05. No effect on success was detected, but with 12 tasks this study could not detect a moderate one, so the success result is inconclusive and should not be read as evidence of no harm. Accurate guidance of this minimal form showed no detectable benefit, which is consistent with Gloaguen et al.'s finding for context files in general.

A possible explanation, not tested here, is that the agent usually searches the repository itself, so a path that does not exist is found to be wrong quickly. A stale path that still exists but no longer holds the relevant code might behave differently.

## 5. Deviations

Changes made before screening and before the confirmatory runs are recorded as amendments in `PROTOCOL.md`: Amendment 1.1 (narrowed to stale file paths; added the relevance and three-validation rules), Amendment 1.2 (three repositories instead of the planned five) and Amendment 1.3 (the planned mixed-effects robustness model replaced by a task-level sign-flip test; preregistration freeze). Deviations after the freeze are recorded in `DEVIATIONS.md`. In brief:

- The confirmatory batch was launched twice by mistake on 2026-10-07; the partial folder was set aside unanalysed and the batch restarted with the same seed.
- 167 of the 276 runs returned session-limit errors (HTTP 429) and never reached the model, spread across conditions (56 accurate, 55 none, 56 stale). The runner's validity check missed them. The invalid-run rule depends only on the error status, not on condition or outcome. These runs were rerun under the unchanged schedule.
- Two rate-limit stops split task-and-repeat blocks; the completed runs of each split block were marked superseded and the whole block was rerun.
- The analysis script was run once on data that still contained invalid runs; those numbers were discarded.
- The runner was fixed to detect such runs; the analysis script and task sets were not changed.
- The stale-following count was corrected from 93 to 92 scheduled runs.

## 6. Limitations

- One agent, one model, one configuration; results may not transfer.
- Three repositories, with 16 of 23 tasks from one.
- One kind of staleness, a file path that does not exist. Renamed symbols, changed commands and outdated architecture notes were not studied.
- A stale path that still exists was not studied.
- The instruction files are minimal; real ones are longer and more varied.
- The success comparison covers 12 tasks and is underpowered.
- The tasks are public, so the model may have seen some of the fixes. This could affect all conditions alike.
- Stale-following was coded automatically by matching paths; no independent rater checked it.
- The cost figure is as recorded by the tooling, not a billed amount.

## 7. Reproducibility

The repository contains the preregistered rubric, scripts, the 50 instruction-file pairs, manifests, screening and confirmatory results, trace coding and the analysis script. The benchmark data and container images come from Multi-SWE-bench and are not redistributed. The raw per-run agent traces are kept locally and are not in the repository, so the primary analysis, which re-codes tool calls from them, cannot be rerun from the repository alone; the committed results folder holds the per-run outputs and the saved analysis output. Rerunning the analysis on the original run folder reproduces the saved output exactly.
